# IEUM Chain 0.21.7 #7 변경 내역

## 결론

이번 4프로세스 BFT 실패의 직접 원인은 **거래 없는 유휴 시간에도 합의 deadline은 흐르지만, timeout 처리는 멈추는 구조**였다.

GitHub Actions 테스트는 P2P 토폴로지를 확인한 뒤 GossipSub 구독을 기다리느라 2초 쉰다. `--git_action_test`의 propose 제한 시간은 1.5초이므로, 송금이 도착할 때는 네 노드의 최초 deadline이 이미 만료되어 있었다. 거래가 수신된 순서대로 각 노드가 즉시 timeout을 처리하면서 round가 갈라졌고, 제안·prevote·precommit이 같은 높이와 round에 모이지 못했다.

로그의 다음 부분이 이 현상과 일치한다.

```text
4노드 P2P 토폴로지 준비 완료: peers=3 1 1 1
0.1 IEUM 송금 제출 완료
[BFT 라운드 변경] ... 새 라운드 1
...
[BFT 라운드 변경] ... 새 라운드 25
```

## geth와 비교

geth는 Ethereum의 실행 클라이언트다. 현재 Ethereum PoS에서는 합의 클라이언트가 슬롯마다 블록 제안 기회를 관리하며, 거래가 없어도 빈 블록을 제안할 수 있다. 과거 PoW geth는 채굴이 동작해야 블록이 생겼다. 따라서 “geth는 거래가 없으면 항상 블록이 생긴다/안 생긴다”로 단순 비교할 수 없다.

IEUM Chain 0.21.7은 현재 거래 또는 예정된 시스템 이벤트가 있을 때만 블록 제안을 시작하는 활동 기반 구조다. 이 정책 자체가 반드시 잘못된 것은 아니지만 다음 조건이 필요하다.

1. 유휴 중 합의 타이머도 함께 정지해야 한다.
2. 첫 작업이 생기는 순간 모든 검증자가 현재 단계 타이머를 새로 시작해야 한다.
3. 제안 이후에는 prevote와 precommit 제한 시간을 계속 적용해야 한다.

이번 구현에는 1번과 2번의 연결이 빠져 있었다.

## 변경 사항

### 1. 유휴 후 합의 타이머 재시작

- `ConsensusRuntime::restart_phase_timeout(now)` 추가
- 거래 또는 원격 제안으로 합의가 비활성 상태에서 활성 상태로 전환될 때 현재 단계 deadline을 새로 계산
- 노드 시작 시점에 생성되어 이미 만료된 deadline으로 즉시 round를 변경하지 않게 수정
- prevote/precommit 진행 중인 정상 timeout과 제안자 교체 규칙은 변경하지 않음

### 2. 회귀 테스트 추가

- 최초 deadline보다 훨씬 늦게 작업이 도착한 상황을 재현
- 타이머 재시작 직후에는 timeout이 발생하지 않는지 확인
- 새 제한 시간이 실제로 지난 뒤에는 정상적으로 다음 round로 이동하는지 확인

### 3. P2P 역직렬화 오류 진단 개선

기존 로그는 다음 한 줄뿐이라 원인을 구분할 수 없었다.

```text
P2P 이벤트 처리 오류: 해석할 수 없는 메시지입니다.
```

이제 payload 원문이나 키를 노출하지 않고 다음 정보만 기록한다.

- 발신 PeerId
- GossipSub topic
- payload 바이트 크기
- serde JSON 오류 위치와 종류

이 변경은 오류를 숨기거나 허용하는 수정이 아니다. 잘못된 메시지는 기존처럼 거부하고 피어 점수를 감점한다.

## 블록 생성 정책

현재 정책은 거래가 없으면 일반 빈 블록을 계속 만들지 않는다. 따라서 블록 높이는 시간만으로 증가하지 않는다. 거래 또는 실행할 시스템 이벤트가 생기면 합의를 시작해 블록을 만든다.

이 정책은 저장 공간과 불필요한 합의를 줄이지만, 시간 기반 슬롯·블록 보상·정확한 블록 주기 등이 필요해지면 별도의 프로토콜 변경이 필요하다. 이번 CI 실패를 고치기 위해 빈 블록 생성을 임시로 추가하지 않았다.

## 다음에 작업할 큰 항목

### FinalityCertificate 중심의 확정 블록 전파와 복구

현재 `PublishBlock`은 확정 인증서 없이 블록만 전파하고, 메인 이벤트 루프에는 `BlockReceived`를 원장에 적용하는 경로가 없다. 이는 안전을 위해 임의 블록을 바로 적용하지 않는다는 점에서는 맞지만, 어떤 노드가 precommit 메시지를 놓치면 블록 전파만으로 복구할 수 없다는 뜻이다.

또한 동기화는 두 개의 독립 피어 응답을 요구한다. CI의 hub-and-spoke 토폴로지에서 leaf 노드는 직접 연결 피어가 hub 하나뿐이므로, 놓친 확정 상태를 즉시 교차검증해 따라잡기 어렵다.

다음 큰 변경에서는 다음을 함께 설계해야 한다.

1. `Block` 단독이 아니라 3개 이상의 유효한 precommit이 든 `FinalityCertificate` 전파
2. 수신 노드가 검증자 집합·높이·이전 해시·서명·상태 전이를 검증한 뒤 적용
3. 직접 연결 수가 적은 노드도 안전하게 복구할 수 있는 인증서 기반 fast sync
4. 중복 인증서와 과거 높이 메시지의 명시적 무시 및 관측 지표
5. 한 노드가 투표/인증서를 놓친 장애를 재현하는 통합 테스트

이 항목은 네트워크 메시지 호환성과 동기화 안전 규칙을 바꾸므로 이번 작은 CI 수정에 섞지 않는다.

## 남은 관찰 항목

새 진단 로그에서 `해석할 수 없는 메시지`가 다시 나오면 topic과 JSON 오류를 기준으로 송신 경로를 추적한다. 동일한 v0.21.7 바이너리 네 개만 실행한 격리망에서도 계속 발생하면 WireMessage 직렬화 경로별 테스트를 추가해야 한다.
