# IEUM 프로젝트 연속성 문서

기준일: 2026-08-27  
대상: `c4ei/ieum-chain`, `c4ei/ieum-manager`, `c4ei/ieum-cold-wallet`, `c4ei/ieum-wallet`

이 문서는 특정 PC나 AI 대화 기억에 의존하지 않고 IEUM 개발·운영을 이어가기 위한 기준 문서다. 새 작업자는 저장소별 `AGENTS.md`, 이 문서, 최신 버전 문서, 최근 GitHub Actions를 순서대로 읽는다. 대화에서 들은 내용보다 소스와 온체인 상태를 우선한다.

## 1. 프로젝트 목적과 비전

IEUM은 한국에서 시작하지만 국가·언어에 묶이지 않는 실사용 중심 블록체인 생태계를 지향한다. 빠른 확정, 이해하기 쉬운 지갑, 오프라인 서명, 투명한 탐색기와 운영 도구를 한 묶음으로 제공한다.

성공 기준은 가격만이 아니다.

- 사용자가 설치·복구·송금·수신을 혼자 완료할 수 있다.
- 노드 장애와 네트워크 분할 뒤에도 안전하게 합의·동기화된다.
- 공급량, 재단 배분, 보상, 상품권 상태가 검증 가능하다.
- 개인키와 운영 키를 서버·GitHub·AI 대화에 노출하지 않는다.
- 홍보 문구보다 실제 동작, 공개 소스, 재현 가능한 테스트를 우선한다.

공식 링크:

- 서비스: https://iem.aah.name
- Chain: https://github.com/c4ei/ieum-chain
- Manager: https://github.com/c4ei/ieum-manager
- Cold Wallet: https://github.com/c4ei/ieum-cold-wallet
- Wallet: https://github.com/c4ei/ieum-wallet

## 2. 생태계 구성과 책임 경계

| 구성 | 책임 | 하지 말아야 할 일 |
| --- | --- | --- |
| Chain | 원장, PoS+BFT 합의, P2P, RPC, 공급·보상 | UI 편의를 위해 합의 불변조건을 약화하지 않는다 |
| Manager | 탐색기, 인덱서, 운영 관제, 상품권, 사용자 안내 | 브라우저나 공개 API에 검증자 키·관리 토큰을 노출하지 않는다 |
| Wallet | 키 생성·복구, 잔액, 송수신, Cold Wallet 연동 | 신원이 다른 RPC에 연결하거나 거래를 자동 재전송하지 않는다 |
| Cold Wallet | 네트워크 없는 금고와 오프라인 검토·서명 | 네트워크·셸·클립보드 권한을 추가하지 않는다 |

운영 메인넷 기준은 Chain ID `21004`, 네트워크 이름 `ieum-mainnet`, IEUM 소수점 18자리다. 공식 genesis hash는 코드·운영 RPC·Wallet 허용값을 함께 대조한다. 기억으로 값을 복사하지 않는다.

## 3. 경제·거버넌스 기준

- 최대 공급량: `210,000,000 IEUM`
- 재단 초기 배분 목표: `21,000,000 IEUM`(최대 공급량의 10%)
- 내부 목적 기준: 장기 준비금·PoS 보상 15,000,000 / 생태계·노드 운영 3,000,000 / 개발·보안·인프라 2,000,000 / 마케팅·상장·유동성 1,000,000 IEUM
- 공급량이나 배분을 바꾸는 변경은 일반 기능 수정이 아니다. 제네시스, 회계 RPC, Manager 표시, 백서와 운영 전환 계획을 함께 검토한다.
- 보상·구매·상품권은 중복 지급 방지, 멱등성, 감사 이력, 장애 복구 경로를 갖춰야 한다.
- 수익·가격 상승·상장을 보장하지 않는다. 공개 홍보에는 기술적 사실, 위험, 개발 단계와 검증 가능한 링크를 사용한다.

## 4. 버전·브랜치·태그 원칙

현재 기준 버전:

| 저장소 | 소스 버전 | 표시/태그 | 안정 릴리스 |
| --- | --- | --- | --- |
| Chain | `1.0.5-1` | `1.0.5.1`, `v1.0.5.1` | 버전별 GitHub Release |
| Manager | `1.0.0-12` | `1.0.0.12` | 서버/Docker 배포 |
| Cold Wallet | `1.0.1-0` | `1.0.1.0`, `v1.0.1.0` | `cold-wallet-latest` |
| Wallet | `1.0.2-1` | `1.0.2.1`, `v1.0.2.1` | `wallet-light-latest`, `wallet-normal-latest` |

하이픈 버전의 마지막 숫자는 사용자 표시에서 점으로 표현한다. 예: `1.0.2-1` → `1.0.2.1`. 저장소에 별도 `version.json`, Cargo/Tauri 버전이 있으면 모두 같은 릴리스를 가리켜야 한다.

- `main`은 배포 가능한 상태로 유지하고 직접 push하지 않는다.
- 기존 `dev`가 있으면 작업 전 `main`과 동기화한다. Cold Wallet처럼 `dev`가 없으면 기능 브랜치를 `main`에서 만든다.
- 기능은 `feature/<short-name>`, 장애 수정은 `fix/<short-name>` 또는 `hotfix/<short-name>`, 문서는 `docs/<short-name>`을 권장한다.
- 기본은 Draft PR이다. CI와 수동 확인이 끝난 뒤 Ready로 바꾼다.
- 코드·사용자 동작이 바뀌면 버전 +1, `docs/VERSION_<version>_<topic>.md`, CHANGELOG/README, 관련 테스트를 함께 갱신한다.
- 문서·주석만 바뀌고 바이너리 동작이 같으면 제품 버전을 올리지 않는다.
- 태그를 먼저 만들지 않는다. PR 병합, `main` CI 성공, 버전 일치 확인 후 annotated tag를 생성한다.
- 릴리스 파일명, 업데이트 manifest, 체크섬과 실제 바이너리 버전을 대조한다.
- 실패한 태그를 재사용해야 한다면 원격 Release/태그/업데이터 영향을 먼저 확인한다. 무조건 삭제·재생성하지 않는다.

## 5. 코딩·검토 습관

- 증상을 가리는 재시작 루프보다 원인과 재현 테스트를 먼저 만든다.
- 금액·잔액·수수료·공급량은 부동소수점으로 계산하지 않는다. 정수 최소 단위 또는 정밀 10진 문자열을 사용한다.
- 전송은 `pending nonce`, 중복 제출, 영수증 확정, 재시작 복구를 함께 검토한다.
- 합의·동기화 변경은 단위 테스트만으로 끝내지 않고 실제 다중 프로세스 네트워크, 지연 노드 재합류, 재시작 보존을 검증한다.
- UI는 한국어를 기본 사용 경험으로 유지하되 영문 및 기존 다국어 키를 깨지 않는다. 어두운 배경의 링크 대비, 모바일 폭, 긴 목록 제한·페이징, 초보자 안내를 확인한다.
- 사용자 소유 변경을 보존한다. 관련 없는 파일을 한 커밋에 섞지 않는다.
- 보안 기능을 임시로 끄는 수정, 시드·키·토큰 출력, 공개 RPC 범위 확대는 금지한다.
- 새 의존성은 필요성, 유지관리, 라이선스, 공급망 위험을 검토한다. Dependabot 메이저 업데이트는 CI 성공만 보고 즉시 병합하지 않는다.

## 6. 완료 정의

작업 완료 보고에는 최소한 다음이 있어야 한다.

1. 바뀐 사용자 동작과 변경 파일
2. 실행한 테스트와 결과
3. 버전 파일 간 일치 여부
4. 보안·마이그레이션·롤백 영향
5. 운영 적용 명령과 적용 후 확인 방법
6. 남은 위험과 실제 확인하지 못한 영역

GitHub Actions 성공은 운영 서버 정상의 충분조건이 아니다. 배포 후 RPC 신원, 높이, 피어, 잔액·nonce·영수증, Manager health, 설치 파일 다운로드를 별도로 확인한다.

## 7. 운영·장애 대응

장애 시 우선순위는 자산 안전 → 합의 안전 → 데이터 보존 → 서비스 복구 → 원인 분석 → 사용자 공지다.

1. 시간, 버전, commit SHA, 노드별 높이·해시·피어·RPC 오류를 기록한다.
2. 개인키·시드·토큰을 제외한 로그와 설정 차이만 수집한다.
3. 거래 중복, 체인 신원 불일치, 다수 노드 분기 가능성이 있으면 자동 재전송·자동 재시작을 중단한다.
4. 원장과 키를 독립 백업하고 복구 대상을 명시한다.
5. 한 번에 한 종류의 변경만 적용하고 각 단계에서 확인한다.
6. 사용자 공지는 확인된 사실, 영향 범위, 임시 행동, 다음 안내 시각을 포함한다. 추측을 사실처럼 쓰지 않는다.
7. 복구 후 재현 테스트와 회귀 테스트를 추가하고 버전 문서에 원인과 예방책을 남긴다.

절대 GitHub·이슈·AI 대화·메신저에 올리지 않을 것: mnemonic/seed, private key, validator key, node key 원문, vault, 비밀번호, JWT/admin token, updater signing private key, 운영 `.env`, 전체 DB/원장 백업.

## 8. 사용자 대응 원칙

- 초보자가 이해할 수 있는 짧은 안내를 먼저 주고, 고급 진단은 접어서 제공한다.
- 송금·복구·콜드월렛은 큰 금액 전에 소액 왕복 테스트를 안내한다.
- 사용자의 거래가 안 보이면 먼저 주소, 네트워크 신원, tx hash, 확정 여부를 확인한다. 시드나 개인키를 요청하지 않는다.
- 429나 RPC 장애는 사용자에게 원인과 재시도 시점을 설명하되 정상 Wallet의 기본 조회·송금 흐름을 과도하게 차단하지 않는다.
- 상품권은 누적 발행과 현재 유효 발행을 구분한다. 폐기·만료가 과거 발행 사실을 지우지 않도록 한다.
- 오류를 숨기거나 성공으로 단정하지 않는다. “GitHub CI 성공”, “운영 확인 완료”, “사용자 기기 확인 필요”를 구분한다.

## 9. 마케팅·성장 원칙

핵심 메시지는 “빠르다” 하나가 아니라 다음 증거 묶음이다.

- 공개 소스와 재현 가능한 테스트
- PoS+BFT 및 노드 장애·재합류 검증
- 일반 Wallet과 네트워크 없는 Cold Wallet
- 투명한 Explorer, 공급·보상·상품권 회계
- Windows/Linux/macOS 설치 파일과 쉬운 한국어 안내
- AAH 생태계와 IEUM의 실제 사용 연결

홍보 글에는 서비스와 네 저장소 링크, 현재 버전, 가능한 기능, 아직 실험/준비 중인 기능, 위험 안내를 함께 넣는다. 투자 수익을 약속하거나 거래소 상장을 확정적으로 표현하지 않는다. AI·개발자·투자 검토자가 읽을 수 있도록 백서와 버전 문서는 구조화된 텍스트로 유지한다.

초기 성장은 설치 수보다 성공 경험을 측정한다: 설치 완료, 첫 백업, 첫 수신, 첫 소액 송금, Cold Wallet 서명, 노드 24시간 가동, 문제 해결 시간. 개인정보를 최소 수집하고 텔레메트리는 사전 고지와 선택권을 둔다.

## 10. 다른 PC·계정에서 재개하기

1. 네 저장소를 clone하고 GitHub 계정·SSH/gh 권한을 확인한다.
2. `git status`, `git remote -v`, 기본 브랜치, 열린 PR, 최근 Actions와 Release를 확인한다.
3. 이 문서와 저장소 `AGENTS.md`, 최신 `docs/VERSION_*`를 새 AI에게 읽힌다.
4. 운영 비밀은 저장소 밖의 기존 보안 저장소에서 복구한다. 새 AI에게 전달하지 않는다.
5. 각 저장소의 기본 테스트를 변경 없이 먼저 실행해 기준선을 만든다.
6. 운영 RPC와 Manager는 읽기 전용으로 신원·상태를 확인한다. 확인 요청만으로 재시작·배포하지 않는다.
7. 가장 작은 작업 하나를 브랜치에서 처리하고 Draft PR로 전체 흐름을 검증한다.

새 AI 시작 프롬프트:

> IEUM 프로젝트를 이어서 작업합니다. 먼저 이 저장소의 AGENTS.md와 docs/PROJECT_CONTINUITY.md를 끝까지 읽으세요. 그 다음 현재 main, 열린 PR/이슈, 최근 Actions, 최신 Release와 버전 파일을 확인해 문서의 기준일 이후 변경을 요약하세요. 비밀정보를 요청하거나 운영을 변경하지 말고, 진단과 변경을 구분하세요. 변경이 필요하면 작은 브랜치와 Draft PR, 버전 일치, 테스트, 버전 문서를 지키세요.

## 11. 기준일 현재 확인 상태

- 네 저장소의 최신 `main` CI는 성공했다.
- Chain `v1.0.5.1` 릴리스와 다중 플랫폼 바이너리·체크섬이 존재한다.
- Wallet `v1.0.2.1` Light/Normal 다중 플랫폼 빌드·서명·latest 갱신이 성공했다.
- Cold Wallet `v1.0.1.0` 다중 플랫폼 설치 파일과 체크섬 생성이 성공했다.
- Manager `1.0.0.12` 테스트, Compose 검증, Docker 이미지 빌드가 성공했다.
- 실제 사용자 이슈는 열려 있지 않고 열린 항목은 Dependabot PR이다.
- `dev`는 기준일에 Chain 1, Manager 22, Wallet 7커밋만큼 `main`보다 뒤였다. 다음 작업 전에 동기화한다.
- Cold Wallet `main`은 기준일에 branch protection이 없었다. 쓰기 권한을 확보하면 보호 설정을 권장한다.
- 이 상태는 2026-08-27의 스냅샷이다. 재개할 때 반드시 GitHub와 운영 상태를 다시 확인한다.
